# Engineering orchestrator

One entry point that runs the existing systems in order and answers one question: **what needs my attention right now?**

```text
Sync ──> Collect ──> Verify ──> Evaluate ──> Prioritize ──> Report
 live      changed     Phase 4      Phase 3      ranked,       reports/engineering/
 revisions evidence    rules        readiness +  deduplicated  + Actions summary
 (git)     only        (overlay)    release      queue
                                    states
```

It adds no service, database or dependency: Node built-ins, GitHub Actions and committed files. It never verifies, approves, merges, publishes or deploys anything.

## Architecture

| Module (`scripts/engineering/`) | Role |
| --- | --- |
| `cli.mjs` | Commands `check`, `report`, `prepare`, `execute` |
| `monitor.mjs` | Live revisions (`git ls-remote`), which collectors need a refresh, registry-sync drift (Phase 2 collector + planner, dry run), remediation PR status. Every API call goes through a GET-only client |
| `manifest.mjs` | Reads `package.json` (root, `packages/*`, `apps/*`), top-level lockfile versions and workflow files at the evaluated commit; never runs them |
| `dependencies.mjs` | Cross-project relationships, shared packages, runtime floors, release order, follow-up verification after a change |
| `release.mjs` | Seven release states and the owner-only transitions; release preparation plan per project |
| `queue.mjs` | Issues from every source, triaged, deduplicated and ranked |
| `evaluate.mjs` | Pure: committed inputs to the result the dashboard shows |
| `prepare.mjs` | Candidate fixes as digested proposals; the gated single-PR execute step |
| `render.mjs` | `reports/engineering/` Markdown and JSON |
| `state.mjs` | `engineering/state.json` (what the last run saw) and the run lock |

It reuses, unchanged in behaviour: `scripts/sync/` (collection, planning), `scripts/verify/` (collectors, evidence, verification rules, overlay, remediation guard) and `scripts/release/` (readiness engine, dependency checks, release preparation drafts). Phase 5 changed two things in them: the dependency-audit collector (1.1.0) now records each advisory's severity, whether it is direct, whether it is reachable from production dependencies (a second `npm audit --omit=dev`) and whether the fix is a major upgrade; and `verify.yml` no longer has its own schedule.

### Files

| Path | Owner | Contents |
| --- | --- | --- |
| `engineering/state.json` | Generated by `check` | Last revision per project, revision change time, manifest per commit, registry-sync drift, remediation PR status, first/last seen per issue, release-state history, last run. Observations only: no verification, approval or governance field |
| `engineering/remediation-prs.json` | Owner (reviewed PR) | Remediation PRs the orchestrator tracks, and which issue ids each covers |
| `verification/policy.json` | Owner (reviewed PR) | Phase 4 governance; `remediation.protectedRepositories` now lists ModsPack, which automation never writes |
| `reports/engineering/` | Generated | `dashboard.md` and `.json`, `queue.md`, `dependencies.md`, `releases.md` |

## Setup and credentials

Nothing is needed to observe public projects: the workflow's own read-only `GITHUB_TOKEN` is enough.

| Credential | Where | Scope | Needed for |
| --- | --- | --- | --- |
| `GITHUB_TOKEN` | automatic | `contents`, `actions`, `checks`, `pull-requests`: read | CI results, PR status, sync drift on public repositories |
| `SYNC_READER_TOKEN` | repository secret (optional) | fine-grained, `contents: read` + `metadata: read` on **one-small-ai-workforce only** | Monitoring the private AI Workforce repository. Without it that project is reported as not readable, never as empty |
| `REMEDIATION_TOKEN` + variable `REMEDIATION_WRITE_ENABLED=true` | repository secret + variable (optional) | fine-grained, `contents: write` + `pull-requests: write` on the one target repository | Opening one draft remediation PR from `remediation.yml`. Leave unset to keep writes off |

Project repositories need nothing. No credential is ever passed to project code: project commands run with an allowlisted environment ([`exec.mjs`](../scripts/verify/exec.mjs)), and the job that runs them holds no secret and no API token.

## Operating modes

| Mode | Command | Writes | Where it runs |
| --- | --- | --- | --- |
| Observe | `npm run engineering:check` (add `--execute` to run project builds and tests) | Local files only: evidence ledgers, `engineering/state.json`, reports. Nothing on GitHub | Schedule (always observe, never executes project code), manual, pull requests |
| Observe (offline) | `npm run engineering:report -- --as-of <UTC>`; `-- --check` verifies the committed reports | Reports only | Anywhere; no network |
| Prepare | `npm run engineering:prepare [-- --project <id>] [--execute]` | Proposal files in `out/engineering/proposals/` (not committed); nothing on GitHub | Manual only; refused on schedules |
| Execute | `npm run engineering:execute -- --proposal <file> --digest <sha256> --confirm` | One draft PR in one project repository | Only through `remediation.yml`, from `main`, by hand |

Execute performs exactly one allowlisted action, `open-draft-pr`. It is refused unless: the proposal's content matches its digest, the digest equals the one you reviewed, `REMEDIATION_WRITE_ENABLED=true`, `REMEDIATION_TOKEN` is set, `--confirm` is given, the run is neither scheduled nor a pull request, the repository is not protected, the files are not workflow files, the findings are for the base commit, and no open remediation PR already covers the issue. The Phase 4 client underneath refuses merge, review, delete, release and settings endpoints and never touches an existing branch.

## GitHub Actions schedule

[`engineering.yml`](../.github/workflows/engineering.yml):

| Trigger | Jobs | Notes |
| --- | --- | --- |
| Every six hours (`17 */6 * * *`) | tests, observe | Read-only. Incremental: only projects whose revision moved, or whose evidence is missing, stale, from another policy or collector version, are collected |
| Manual, `mode: observe` | tests, (execute), observe | `execute: true` first runs project builds and tests in a separate job with no secret, then observes |
| Manual, `mode: prepare` | tests, prepare | Proposals and their digests as an artifact; nothing is written |
| Pull request touching the orchestrator | tests, observe | The PR's code runs with a read-only token and no reader secret |

Top-level `permissions: {}`; every job asks for read permissions only; actions are pinned to commits; credentials are not persisted; each job has a timeout; API calls retry a bounded number of times and a long rate-limit wait is skipped (the next run catches up). Runs on one ref queue instead of overlapping (`concurrency`, `cancel-in-progress: false`), and a local run holds `engineering/.lock`. State between scheduled runs lives in the Actions cache (written only by runs on `main`, never by pull requests). Every run uploads reports, state and evidence for 30 days, and the job summary shows the dashboard.

[`verify.yml`](../.github/workflows/verify.yml) keeps its manual and pull-request triggers for verification work; its daily schedule moved here so evidence is not collected twice. [`registry-sync.yml`](../.github/workflows/registry-sync.yml) still owns registry updates (stages A/B/C); the orchestrator only reports what a sync would change.

## Manual verification workflow

1. Run the workflow by hand with `mode: observe`, `execute: true` (or locally `npm run engineering:check -- --execute`; use the Node version a project's `engines` asks for).
2. Download the `engineering-<run>` artifact, or read the dashboard in the job summary.
3. The verifier named in the registry re-checks the evidence for the exact commit and records it outside CI: `npm run verify:record -- ...` ([docs/verification.md](verification.md#independent-verification)). Open a PR with the record. Only that raises readiness.
4. To keep evidence from an Actions run, commit `verification/evidence/` and `engineering/state.json` from the artifact in a hub PR.

## Remediation authorization workflow

1. Read `reports/engineering/queue.md`. Issues marked *Automatically actionable* have a deterministic fix (today: a lockfile-only dependency update within declared ranges; never `--force`).
2. Run `engineering.yml` by hand with `mode: prepare` (and `execute: true` to run the project's tests against the fix). The artifact holds one proposal per issue and `README.md` with each digest. Proposals that would not resolve the issue, or that fail the project's tests, are listed as not prepared and stay issue reports.
3. Review the proposal (files, branch, PR body, validation, rollback).
4. To open it: set `REMEDIATION_WRITE_ENABLED=true` and `REMEDIATION_TOKEN` (scoped to that repository), run `remediation.yml` from `main` with the issue id, the digest you reviewed and the confirmation text. The proposal is prepared again in a step without the token; if anything changed, the digest differs and nothing is opened.
5. Add the new PR to `engineering/remediation-prs.json` in a hub PR so later runs track it and never prepare the same fix again. Turn writes off again if you like.
6. Review, test and merge the project PR yourself, or close it. Nothing is merged automatically.

## Release preparation workflow

`reports/engineering/releases.md` gives each project's state, candidate revision, missing verification, blockers, dependency readiness, required manual testing, required approvals, version and rollback.

| State | Means | Moves on when |
| --- | --- | --- |
| Not Ready | No target version or scope document | The owner scopes the release in the registry |
| Blocked | Open registry blocker, critical/high defect at the evaluated commit, unreleased required dependency, moved candidate, or the repository cannot be read | The cause is fixed and recorded |
| Verification Required | Scoped, nothing blocking, gates lack independent verification (or no builder/verifier, or no candidate) | The verifier records every pre-publication gate at the candidate |
| Candidate Ready | Every pre-publication gate verified at the recorded candidate | Draft the release with `npm run release:prepare`; the owner sets `releaseStatus: ready_for_review` |
| Awaiting Human Approval | Up for the owner's review | Joshua Small's approval is recorded with evidence **for the candidate commit** |
| Approved for Release | Approval valid and bound to the candidate | The owner merges, tags, publishes or deploys, then records the release |
| Released | The registry records the release with approval | |

An approval by anyone else, recorded by automation, without evidence or for another commit never produces Approved for Release. The system prepares checklists, release notes, changelog drafts, compatibility notes and rollback steps; publishing, merging and deployment stay owner actions.

## Reading the dashboard

`reports/engineering/dashboard.md`:

- **Attention now**: the top ten non-informational issues. Each has one next action.
- **Portfolio**: projects, release states, failing CI, security findings by severity, verification coverage, open and unreviewed remediation PRs, stale evidence, dependency risks, and the queue split by action class.
- **Projects**: revision, when it was first seen, access, CI at that revision, verified gates, release state (and the previous one when it changed), blockers, security counts, open PRs, registry-sync drift and the next action.

The queue (`queue.md`) ranks by priority class (1 critical security, 2 broken build or failing required CI, 3 release-blocking, 4 high vulnerability, 5 cross-project compatibility, 6 accessibility, 7 missing verification or documentation, 8 technical debt), then severity, then project order, and groups by action: automatically actionable, requires independent verification, requires owner decision, blocked by credentials or environment, informational. Advisories are triaged by reachability: a critical advisory only in development tooling ranks below one in production dependencies, and a fix that needs a major version is an owner decision, not an automatic change.

Issue ids carry no commit (`project:source:key`), so the same problem keeps its id, its first-seen date and its PR link across revisions. "Unavailable" and "no current evidence" mean unknown, never pass.

`dependencies.md` separates confirmed relationships (evidenced registry declarations, package manifests, workflow files) from suspected ones (declarations without evidence), lists projects that need re-verification because something they depend on changed, and shared third-party packages with advisories or diverging major versions.

## Common failures and recovery

| Symptom | Cause | Recovery |
| --- | --- | --- |
| `another orchestrator run holds engineering/.lock` | A local run is active, or one crashed | Wait; a lock older than three hours is replaced automatically, or delete the file if no run is active |
| `engineering/state.json is not valid JSON` / `is invalid` | Hand edit or bad merge | `git checkout -- engineering/state.json`, or delete it: the next run rebuilds it (first-seen dates restart) |
| AI Workforce "not readable" | No reader credential | Add `SYNC_READER_TOKEN`, or take the project out of monitoring by owner decision |
| ci-results, PR status or sync drift "unavailable" | GitHub API not reachable from that machine, or rate-limited | Run in Actions; statuses from the last successful read are kept and labelled |
| build-test "inconclusive: below the engines floor" | Runner Node older than the project needs | Run with the Node version the project declares (the workflow uses Node 24) |
| `report --check` fails | Reports edited, or inputs changed without regenerating | `npm run engineering:report -- --as-of <time in the message>` |
| Execute refused: digest does not match | The fix was prepared again and came out different (new upstream versions) | Run `mode: prepare` again, review the new proposal, use its digest |
| Execute refused: branch already exists | An earlier attempt created it | Look at that branch or PR; it is never rewritten. Delete it yourself if it is unwanted |

## Rollback

Everything Phase 5 adds is additive. To roll back, revert its PR: that removes `scripts/engineering/`, `engineering/`, `reports/engineering/`, `engineering.yml`, this document and the npm scripts, restores `verify.yml`'s daily schedule and `remediation.yml`'s plan-only input, and returns the dependency-audit collector to 1.0.0 (its next run records evidence without advisory detail). To stop only the schedule, disable the *Engineering orchestrator* workflow in the Actions tab. To stop writes, unset `REMEDIATION_WRITE_ENABLED`; nothing else can write to a project repository.
